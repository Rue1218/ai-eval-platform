## 1. 结论：你的总体方向是对的，但有四个关键边界需要校正

图表达的主线是正确的：Agent 并不是“一个大模型”，而是 **大模型 + Harness（受控运行时）**。Harness 在模型调用前准备恰当上下文，在模型提出动作后执行受限动作，并把可信观察结果反馈给模型，形成闭环。

但下列等式不成立：

```text
提示词工程 = 纯文本 CoT                  ×
上下文压缩 = 召回 / RAG 检索              ×
系统提示词 + 用户提示词 + 工具 = 记忆层    ×
模型的原始思维链 = 可持久化业务状态         ×
```

更准确的关系是：

```text
提示词工程        定义模型本轮的角色、约束、输出契约和动作协议
上下文工程        按本轮目标选择、裁剪、排序并装配“模型可见输入”
记忆层            保存可复用状态，并按需要检索/摘要后交给上下文工程
编排层            决定本轮采用 Chat、ReAct、Plan-and-Solve 还是直接控制
执行层            在权限、参数、超时、隔离和确认边界内真正产生副作用
反馈层            将工具观察、校验结果和外部任务事件变成下一步的可信依据
```

因此，Harness 是把这些层串成一个 **受权限、预算、状态机和可追溯性约束的控制系统**；模型只是其中的推理与语言决策组件。

## 2. 分层总图：控制面与执行面

```text
                           ┌──────────────────────────────────────┐
                           │        产品/安全确定性约束             │
                           │ 工具注册表 · 权限 · 门禁 · 预算 · 审计 │
                           └────────────────┬─────────────────────┘
                                            │
用户消息/附件                               │                           长耗时任务
      │                                     │                              │
      ▼                                     ▼                              ▼
┌──────────────┐                    ┌────────────────┐             ┌──────────┐
│ 传输与会话层 │──持久化事件/状态──►│   Harness 控制面 │──确认后───►│ Worker   │
│ WS/REST/鉴权 │                    │                │             │ 执行面   │
└──────┬───────┘                    │ 1. 上下文编译   │             └────┬─────┘
       │                            │ 2. 编排与调用   │                  │
       │                            │ 3. 工具治理     │        progress/report/error
       │                            │ 4. 规则复核     │                  │
       │                            └───────┬────────┘                  │
       │                                    │                           │
       │                               模型调用/短工具                  │
       │                                    ▼                           │
       │                           ┌────────────────┐                  │
       └──────────────────────────►│      大模型     │◄─────────────────┘
                                   │ 受限的结构化决策 │    只按需成为上下文
                                   └────────────────┘
```

这里要区分两个闭环：

| 闭环 | 目的 | 时长 | 是否由模型连续等待 |
| :--- | :--- | :--- | :--- |
| 回合内 ReAct 闭环 | 取得短工具观察、调整下一动作并交付 | 秒级 | 是，但受轮数、墙钟和 `/stop` 限制 |
| 任务生命周期闭环 | 排队、评测、报告、压测等长任务 | 分钟或更长 | 否；Worker 仅写事件，用户下一条消息才开启新回合 |

把第二种闭环直接塞回同一轮模型上下文会导致连接阻塞、无关进度淹没任务目标和上下文污染。因此 Worker 的全部日志不是自动记忆；只有被用户询问或被工作流明确选择的摘要才应进入后续上下文。

## 3. 提示词工程：不是“要求模型展示 CoT”

### 3.1 正确职责

提示词工程的工作是设计 **模型—Harness 协议**，不是把模型自由推理文本当作程序控制面。它至少包含：

1. **角色与边界**：允许做什么、绝不做什么、何时明确拒绝。
2. **输入语义**：用户请求、附件、历史、可信观察分别是什么。
3. **输出契约**：要求 JSON 字段、枚举值、最大动作数与结束条件。
4. **动作协议**：只能提出注册表内工具、参数由系统绑定、一次至多一个工具。
5. **失败语义**：观察失败不等于任务失败；应基于错误决定澄清、重试、降级或交付。
6. **安全策略**：用户内容不能改变系统角色、扩展工具权限或索取密钥。

当前实现将这些职责拆成阶段提示词：

| 提示词 | 作用 | 当前状态 |
| :--- | :--- | :--- |
| `PERSONA_SYSTEM` | 固定职责、安全与业务边界 | 已实现 |
| `PLAN_JSON_SUFFIX` | 产生受限的 `PlanArtifact`，选择 `chat` 或 `react` | 已实现 |
| `REACT_LOOP_SUFFIX` | 约束 `thought/tool/arguments/done/reply` 结构化决策 | 已实现 |
| `COMPACT_SYSTEM` | 只摘要目标、未决事项与必要状态，排除敏感信息 | 已实现 |
| `REFLECT_CHECK_SUFFIX` | 预留的模型辅助复核契约 | 代码保留，当前最小内核未启用 |

### 3.2 CoT、可见 thought 与结构化推理的边界

“CoT”在工程上至少可能指三件不同的事，必须分开：

| 名称 | 含义 | 是否应成为系统事实来源 |
| :--- | :--- | :--- |
| 模型内部推理 | 模型生成答案时的隐式计算过程 | 否；不可依赖、不可作为授权依据 |
| 面向用户的 thought | 简短解释性进度，例如“正在根据参考图生成图片” | 可展示/审计，但不是权限凭证 |
| 结构化决策产物 | Plan、工具调用、确认规格、门禁结论 | 是；必须被解析、校验和持久化 |

图中的“思考”可以理解为 **模型参与决策**，但不应定义为“必须输出完整纯文本思维链”。长文本任务也不靠暴露 CoT 来保证正确性；更可靠的方法是：分块输入、显式任务状态、结构化中间产物、检索证据、确定性校验和可验证输出。

当前 ReAct 可以流式显示模型提供的 `reasoning_content`，并在结束后保存 `think_final` 快照；这仅用于用户体验和问题排查。真正驱动工具执行的是已解析的 `tool` 与 `arguments`，真正决定是否放行的是注册表和确定性门禁，二者都不能由 thought 覆盖。

### 3.3 用户提示词不是系统提示词的可编辑续写

上下文编译时，系统规则与用户原文应维持明确的消息边界：

```text
system：产品角色、工具协议、安全边界、输出 schema
system：按需加入的技能说明、压缩摘要
user：用户本轮原文和经过验证的附件引用
user/structured：本轮 Plan、工具 observation 或复核输入
```

用户可以改变“要完成什么”，不能改变“能调用什么、谁有写权限、什么算成功”。这是抵抗提示词注入的基础。不要通过字符串拼接把用户输入拼入系统规则，也不要让网页配置把用户自定义系统提示词覆盖产品策略。

## 4. 上下文工程：运行时的“上下文编译器”

上下文工程不只是管理窗口长度或防幻觉，而是决定每次模型调用的全部可见输入。一个可靠的上下文编译器要同时优化：

```text
相关性（回答当前问题）
一致性（目标、约束、事实不冲突）
可验证性（每条关键事实有来源）
安全性（用户输入不能越权）
容量与成本（不超过窗口且控制延迟）
```

### 4.1 本项目的上下文装配顺序

当前 `turn_system()` 的系统侧顺序是：

```text
固定 Persona + 当前阶段输出协议
    → 可选 Skill Hint
    → 可选 compact_summary
```

随后每个阶段在自己的 payload 中加入必要输入，而不是把数据库全部内容、全部工具 schema 和所有事件一次性塞给模型：

| 阶段 | 主要输入 | 为什么这样做 |
| :--- | :--- | :--- |
| Planner | 本轮文本、最近消息窗口、偏好、附件标识 | 识别当前目标与循环，不直接执行 |
| ReAct | 用户原文、Plan、已发生的 observation、必要历史 | 只根据可信工具结果决定下一步 |
| Chat | 用户原文、最近消息窗口、摘要 | 不携带无关工具噪声 |
| Compact | 被选中的旧消息 | 生成可控摘要，不能删除原始审计记录 |

**工具定义不是默认全量记忆。** 正确做法是由能力注册表选择本轮可用工具描述，并以最小权限方式注入；当前最小内核仅有 `audio.voiceclone` 与 `image.generate` 两项。工具结果也不应原样反复注入，而应变成带来源、状态、计数、ID 与错误码的 observation 摘要。

### 4.2 当前窗口与事件的不同职责

`context.py` 当前的窗口算法只保留 user/assistant 最终交付消息：

```text
全部 user + assistant messages（按时间升序）
  → 若有 compact_keep_from，则从该消息开始
  → 至多取末尾 20 条
  → 供规划和闲聊模型使用
```

`thought`、`tool_call`、`tool_result`、确认卡、进度和报告是 `ws_events`，用于前端回放、断线重连与审计，**不是默认进入聊天窗口的文本**。ReAct 只会将本轮工具结果的压缩 observation 反馈到下一步，以免大对象、错误堆栈或长任务进度污染上下文。

这正是“上下文工程最容易出错”的位置：若把不可信用户文本、未脱敏工具原文、过时摘要或全量任务日志混入模型输入，模型即使能力很强也会被错误事实和注意力竞争误导。

### 4.3 上下文选择优先级、来源和最小注入

上下文不应按“谁最近出现就放谁”来拼接，而应先判断来源和权限。建议的事实优先级为：

```text
确定性安全/产品规则
  > 已鉴权且由系统读取的当前状态
  > 本轮受控工具 observation（带工具名、时间和成功状态）
  > 用户明确表达的目标与偏好
  > 带来源的历史原文或检索片段
  > 压缩摘要
  > 模型自己生成的计划、thought 与猜测
```

这不是说用户目标不重要，而是说用户不能用一句“忽略前文”覆盖权限或工具事实；模型产物也必须回到 schema/门禁后才可成为状态。每项被放入上下文的内容都应回答：**它来自哪里、是否仍有效、是否有权看到、是否是本轮需要的最小内容？**

技能与 MCP 也适用最小注入原则：

```text
意图/回合模式
  → 选择一个 Skill Hint（可选）
  → 选择本轮允许工具的精简 manifest
  → 执行后仅注入结果摘要 observation
```

不要把所有技能全文、全部历史工具结果和所有工具 schema 永久置入每个回合。这样既浪费 token，也会让模型把无关能力误认为当前可调用能力。

## 5. 记忆层：保存、检索、压缩、排序不是同一个动作

可以把记忆层拆为四类，而不是将所有 prompt、skill 和工具统称为“记忆”。

| 类型 | 保存什么 | 当前实现 | 进入模型的方式 |
| :--- | :--- | :--- |
| 工作记忆 | 本轮 Plan、观察、停止标志、工具轮数 | 已实现，进程内/本轮对象 | 仅本轮按阶段传入 |
| 情景记忆 | 会话消息、事件、确认卡、任务状态 | 已实现，PostgreSQL | 近期消息进入窗口；事件按需回放 |
| 压缩记忆 | 旧对话的摘要和保留起点 | 已实现，手动 `/compact` | `compact_summary` 作为系统侧摘要 |
| 偏好记忆 | 确认成功后记录的受限用户偏好 | 代码保留；随业务工作流状态受限 | 作为建议，不能绕过校验 |
| 语义/知识记忆 | 可检索的文档片段、向量、实体关系 | 当前未接入 | 后续须显式检索并带来源 |

### 5.1 四个常被混淆的操作

```text
召回 / Retrieval
  从大量外部或长期记忆中，按当前问题找出候选证据。

重排序 / Reranking
  对“已召回候选”按相关性、时效、权限、可信度重新排序。

压缩 / Summarization or Compaction
  在保留目标、约束、事实来源和未决事项的前提下减少 token。

编排 / Context Assembly
  按固定优先级将系统规则、事实、摘要、工具和用户输入放到正确位置。
```

它们可组成类似 RAG 的流水线：

```text
候选记忆/文档 → 过滤（权限、时效、来源） → 召回 → 重排序 → 压缩 → 上下文装配
```

但当前 `/compact` 并没有完成整条 RAG 流水线。它只是：保留最近 6 条消息，调用模型摘要更旧的当前窗口内容，将摘要写入 `sessions.compact_summary`，并保留原始 messages/events 不删除。当前没有向量数据库、语义召回或自动记忆检索。因此，“压缩就是召回 + 重排序”是未来可扩展的设计，而不是现行事实。

### 5.2 对摘要的正确治理

摘要是有损表示，必须被当作“可更新的派生状态”，不能当作唯一真相。它至少应保留：

1. 用户目标及成功标准；
2. 已确认事实及其来源；
3. 还未解决的歧义或下一步；
4. 明确的约束、授权和拒绝历史；
5. 不含密钥、Cookie、原始上传敏感内容和工具内部异常。

当原始记录与摘要冲突时，原始的带来源状态优先；摘要应被重建或修正。对于高风险写操作，永远不能只凭摘要授权，仍应重新读取权威对象并经过门禁。

### 5.3 记忆写入、更新与失效

完整的记忆层除了“读取什么”，还必须规定“何时写入、谁可以覆盖、何时失效”：

| 状态 | 合法写入时机 | 覆盖/失效规则 |
| :--- | :--- | :--- |
| 用户消息与最终交付句 | 收到/完成回合时 | 原文追加，不用摘要覆盖 |
| 工具事件 | 调用和返回时 | 追加审计事件；结果只在本轮作为 observation 使用 |
| 计划和 thought | 回合内 | 只是暂态或审计快照；未经门禁不能升级为事实 |
| 压缩摘要 | `/compact` 成功后 | 新摘要替代旧摘要，但原始记录保留；冲突时重建 |
| 用户偏好 | 已确认的业务写操作成功后 | 仅保存允许字段，并在下一次使用前再次验证 |
| 检索知识 | 检索时 | 带来源、版本和权限；过期或撤权后不得再注入 |

尤其不应把模型的原始 reasoning、失败堆栈或用户粘贴的任何长文本无条件写成“长期记忆”。前两者不是可靠事实，后者还可能携带提示注入、个人数据或过期指令。

## 6. 编排层：复杂任务用 Plan-and-Solve，短任务用 ReAct

### 6.1 编排不是“再写一段长 CoT”

编排层的职责是选择合适的控制流，并生成可验证的中间状态。复杂度判断、任务拆解、依赖关系与停止条件可以由模型建议，但必须收敛为结构化 schema，例如：

```json
{
  "intent": "chat",
  "tools_needed": ["image.generate"],
  "delivery": "text",
  "complexity": "medium",
  "loop": "react"
}
```

这是“结构化推理产物”，而不是要求模型暴露未受约束的推理链。Harness 必须校验枚举、工具白名单、预算和状态转换；不合法的计划只能降级、澄清或拒绝。

### 6.2 目标架构的模式选择

| 模式 | 适合的任务 | 过程 |
| :--- | :--- | :--- |
| Direct | `/stop`、`/compact` 等确定性控制 | 不让模型决定副作用 |
| Chat | 闲聊、说明、无需工具的回答 | 直接生成交付文本 |
| ReAct | 一到数步的受控短工具任务 | Think → Act → Observe，至多一工具/轮 |
| Plan-and-Solve | 多槽位、依赖多、包含确认卡或长任务的工作流 | 计划 → 分步执行 → 门禁/核对 → 人工确认 → 异步 Worker |

复杂任务应在 Plan 中显式包含：目标、约束、子任务、依赖、所需证据、可用工具、预算、完成判定和失败处理。执行每个子任务后，应只把经过治理的结果写入状态，再由编排器决定继续、重试、补计划、澄清或停止。

### 6.3 当前实现状态

现行最小内核确实保存了 `PlanArtifact`、`TurnMode`、`run_gates()` 和 `maybe_model_check()` 的通用骨架，但业务工作流已在重构中：

```text
当前对外路线：Direct（/stop、/compact） + Chat + ReAct（两项多媒体工具）
当前未启用：Benchmark/RAG/用例编排、资产查询、确认卡下单、补规划、模型复核
```

具体来说，`persona.py` 当前把 `intent` 限为 `chat`，`tools_needed` 限为两项多媒体工具；`turn_mode.py` 将补规划和模型核对返回 `False`。因此图中的“编排层/结构化 CoT”描述的是 Harness 应有的扩展架构和保留代码骨架，不能误称为当前已完整开放的评测业务能力。

## 7. 执行层与 ReAct：模型提议动作，Harness 执行动作

### 7.1 回合内 ReAct 状态机

```text
用户目标 + 已编译上下文
          │
          ▼
  模型输出 McpStep JSON
  { thought, tool, arguments, done, reply }
          │
          ├─ done=true / tool=null ───────────────► 交付 reply
          │
          ▼
  注册表查找、权限/白名单检查
          │
          ├─ 不允许 ─► 结构化失败 observation ─┐
          ▼                                   │
  系统绑定附件参数、脱敏日志、超时隔离           │
          │                                   │
          ▼                                   │
  执行一个短工具 → tool_result → observation ──┘
          │
          ▼
  下一轮模型：继续、修正、澄清或结束
```

这正是你所说的“执行出错后送回上下文再处理”，但要加两个限制：

1. 送回的是规范化 observation（工具名、成功标志、可读错误、延迟、必要结果摘要），不是完整异常堆栈或秘密数据。
2. 失败反馈不意味着模型可以无限重试；必须有轮数、总时限、幂等/去重和用户授权限制。

### 7.2 当前最小 MCP 内核

`mcp_registry.py` 是工具元数据、参数绑定和执行分派的唯一来源。当前仅注册：

| 工具 | 权限 | 系统绑定的关键约束 |
| :--- | :--- | :--- |
| `audio.voiceclone` | write | 参考音频必须来自本轮 wav/mp3 附件 |
| `image.generate` | write | 参考图必须来自本轮图片附件；提示词可由模型建议 |

执行层做的不是“任意运行命令、任意读写文件”。它只允许注册的受控能力，并负责：参数绑定、用户归属、超时、线程隔离、脱敏、结果截断、事件落库和错误归一化。`task.create` 不属于当前 MCP；未来恢复评测业务时也必须保持“确认卡 `confirm_ack` 后才创建队列任务”的授权边界。

### 7.3 API 与 Worker 的边界

Agent API 是控制面，绝不在对话回合里等待 Benchmark、RAG、用例生成或压测完成。未来的受控任务链必须是：

```text
Plan-and-Solve 组出规格
  → 确定性门禁
  → 用户确认
  → 创建 queued task
  → Worker 独立执行
  → 状态/进度/报告事件持久化
  → UI 实时展示或断线重放
```

这不是 ReAct 单回合的一部分，而是受数据库状态机保护的外层业务循环。

## 8. 反馈层：观察、门禁与用户反馈各有职责

“反馈层”不应只理解为工具报错回填模型，它有三层：

| 反馈类型 | 发送给谁 | 作用 |
| :--- | :--- | :--- |
| Tool observation | 下一轮 ReAct 模型 | 决定继续、调整或停止 |
| Deterministic gate | Harness | 强制校验工具、参数、状态、权限和确认边界 |
| 用户/Worker 事件 | 用户界面与后续回合 | 展示进度、报告、错误并形成可追溯记录 |

### 8.1 ReAct、反馈与 Reflection 不是同义词

| 术语 | 最小定义 | 在图中的位置 |
| :--- | :--- | :--- |
| Reasoning | 模型根据已编译上下文提出下一步结构化决策 | 模型内部/输出 `McpStep` |
| Acting | Harness 执行已授权的工具或状态转换 | 执行层 |
| Observation | 工具结果、错误或状态摘要 | 反馈给下一轮 ReAct 的输入 |
| ReAct | `Reason → Act → Observe → 再 Reason` 的回合内控制循环 | 编排层与执行/观察之间 |
| Feedback | 更宽的反馈平面，包含 observation、门禁、用户确认和 Worker 事件 | 横跨执行层、状态层和上下文工程 |
| Reflection | 对计划/结果做额外复核的策略；必须有可验证信号 | ReAct 外层的可选质量关卡 |

因此可以说“工具错误反馈参与 ReAct”，但不能说“反馈层就是 ReAct”。ReAct 关心本轮下一动作；反馈层还关心用户是否看见、状态是否持久化、Worker 是否完成、以及未来回合该检索什么。

目标架构中，Reflection 应采取“规则优先、模型辅助”的方式：

```text
结构化计划 + 工具观察 + 当前会话状态
     → 确定性 Gates（必经，能 reject）
     → 可选模型核对（只能提出 clarify，不能越权放行）
     → pass / clarify / reject
```

这比让模型仅凭自然语言“自我反思”可靠：模型可以帮助发现目标不清楚，却不能绕过资产来源、权限、并发占槽、长短任务隔离和人工确认等硬约束。

## 9. 当前一次消息的实际运行顺序

以当前已经开放的聊天、生图和配音能力为例：

```text
1. 浏览器发送 user_message（文本 + 已校验附件 ID）
2. WS 路由把用户消息和事件持久化，并启动独立 Harness 回合
3. Harness 读取最近消息窗口、压缩摘要和用户偏好
4. Planner 输出受限 PlanArtifact（chat 或 react；上游失败则 L0 降级）
5. TurnMode 选择：/stop|/compact → Direct；无需工具 → Chat；多媒体 → ReAct
6. ReAct 每轮请求模型给出一个 McpStep JSON
7. Harness 只从注册表执行一个允许的短工具，写 tool_call/tool_result
8. 工具结果变为脱敏 observation，供下一轮模型决定
9. 模型 done 或达到上限后，Harness 写最终交付句
10. UI 从事件流展示 thought、ToolCall、工具结果和最终消息；断线按 event_id 回放
```

注意第 7 步：Harness 不是把工具“加载进上下文后任由模型运行”，而是模型提出一个意图，Harness 作为可信执行器复验后才调用。模型不能伪造附件 ID，也不能自行扩大工具集合。

## 10. 对原理解逐项核对

| 你的表述 | 判断 | 校正后的表述 |
| :--- | :--- | :--- |
| Agent = 大模型 + Harness | 正确 | Harness 是控制、状态、工具、安全和可观测性运行时。 |
| 提示词工程是纯文本 CoT，用于长文本任务 | 需要校正 | 提示词工程定义行为/输出协议；CoT 不是其同义词，长任务可靠性依赖结构化状态与校验。 |
| 系统提示词编排规范，用户提示词受其约束 | 正确 | 需保持 system/user 边界，用户不能覆盖系统策略。 |
| 上下文工程管理窗口，是幻觉高发点 | 基本正确 | 还负责相关性、来源、安全、成本、工具/状态最小化注入。 |
| 系统提示词、用户提示词、skill、MCP 放进上下文 | 部分正确 | 它们按需进入“模型输入”；固定 prompt 与工具注册表本身不是记忆。 |
| 压缩机制是召回、压缩、编排、重排序 | 需要拆开 | 召回、重排序、压缩、编排是不同阶段；当前只实现手动摘要压缩，不含 RAG 检索。 |
| 这两个工程合为记忆层 | 需要校正 | 提示词/上下文工程服务于记忆层，但记忆还包括持久化、来源、检索和生命周期。 |
| 执行层调用工具、命令、文件 | 方向正确 | 必须是注册且获授权的动作；当前不支持任意命令或文件读写。 |
| 工具错误回到上下文给模型处理，是 ReAct | 正确 | 回传应为脱敏、截断、结构化 observation，并受重试/预算约束。 |
| 复杂任务需要规划、拆解，是结构化 CoT | 基本正确 | 更准确叫“结构化计划/状态机”；模型提出计划，Harness 校验、调度和执行。 |

## 11. 后续演进建议：恢复评测 Workflow 时的正确顺序

当 Benchmark、RAG、资产检索和确认卡工作流重新接入时，应按以下顺序恢复，而不是先扩充提示词：

1. **领域状态与 schema**：定义 Plan、TaskSpec、证据来源、失败/重试/完成条件。
2. **受控工具注册表**：为每项工具定义读写权限、参数绑定、超时、幂等性和审计。
3. **确定性 Gates**：实现资产可溯源、并发占槽、确认授权、长短任务隔离。
4. **Plan-and-Solve 编排**：根据复杂度、依赖和预算选择步骤；每步只消费可信 observation。
5. **持久化记忆与检索**：若接入语义记忆/RAG，必须有权限过滤、来源引用、重排序和摘要失效策略。
6. **模型辅助复核**：仅用于发现歧义或提出澄清，永不替代确定性授权。
7. **可观测性与评估**：记录决策版本、输入来源、工具调用、门禁结果、延迟与用户纠正，建立可回放评测集。

这样，提示词优化是最后的“协议质量调优”，而不是用自然语言掩盖缺少状态机、证据链和执行边界的问题。

审查任何新增 Agent 能力时，应逐项回答：

1. 此能力的输入事实来自哪里，是否可溯源、是否经过权限过滤？
2. 哪些内容应进入本轮上下文，哪些只能留在事件/数据库中？

5. 失败会以何种脱敏 observation 反馈，何时停止而不是无限循环？
6. 写操作是否经过人工确认、事务与长短任务隔离？
7. 当前实现、设计目标和暂未启用能力是否被明确区分？
