## 1. 目标、范围与权威依据

目标是在保留对话、后台任务、审批、权限撤销和断线恢复行为的前提下，同时做到响应快、资源占用低。首字、流式显示、取消、会话切换和重连不能因减负而出现可重复的性能退化；降低空闲会话及流式输出对 API、PostgreSQL 和浏览器的开销必须与速度验收同时通过。

本方案优先处理重复请求、重复查询、无效轮询和闲置资源；不通过降低模型质量、删除持久事实、跳过鉴权、绕过沙箱或扩容掩盖问题。模型供应商推理速度与平台自身处理耗时分别测量。

### 1.1 速度与资源的共同约束

| 设计原则 | 实施要求 |
| --- | --- |
| 减少工作量，同时缩短等待 | 优先请求去重、批量查询、共享增量读取、缩短行锁事务和按需快照；这些改动应同时减少资源消耗与请求排队 |
| 活动链路即时处理 | 用户发送、取消、审批/澄清应答、首个输出片段和持久终态不等待空闲轮询或批量定时器 |
| 有变化才唤醒 | 提交后的事件提示唤醒增量读取，空闲时等待；通知不可靠时仍用有界兜底读取确保正确性与时效 |
| 缓存与回收都有上限 | 优先请求内复用；跨请求缓存须有容量和失效规则。释放后台空闲连接时保留有界恢复状态，避免频繁冷启动；不能无限保留 Runtime 换取速度 |
| 相同负载下同时对照 | 固定机器、并发、模型输出和历史规模，比较延迟、吞吐、错误率及 CPU/数据库/内存；不能通过降低请求量、拖长处理时间或转移到浏览器耗能制造收益 |

**禁止把 WS 的 100ms 轮询直接改成数秒等待作为主要优化交付。** 通知覆盖、共享读取和兜底时效尚未验证的路径，先消除重复查询、全量扫描与锁竞争，再决定是否允许延长空闲等待。速度预算与资源预算按 §5 同时判定，任何一侧未达标都不能宣称优化完成。

- [API 契约](AI测试与评估平台-API.md)：REST 与 WS v2 字段、游标、权限和终态语义。

## 2. 当前链路与证据边界

### 2.1 通信职责

| 链路 | 当前用途 | 本次关注点 |
| --- | --- | --- |
| `GET /api/sessions/{id}/agent-ui`；草稿使用 `/api/sessions/agent-ui` | 获取模型、专家、思考档位、权限、控制状态和附件限制 | 请求频率、重叠请求、重复配置解析 |
| `/ws/agent/v2` | 提交 `turn.submit`、取消、交互回复、流式输出及持久事件回放 | 后端轮询、逐帧鉴权、连接保留、快照开销 |
| 平台 → 模型 HTTP(S)/SSE | 官方 SDK 请求与响应流 | 连接资源、供应商耗时和平台耗时分离 |
| Worker → 持久事件 → WS v2 | 评测等长任务的进度与终态 | 事务桥接、补偿扫描、重复投影检查 |

`agent-ui` 是页面配置接口，不提交回合、不调用模型。将它改为 WS 消息本身不会消除其背后的重复计算，不能把“全部改成 WebSocket”当作减负方案。

### 2.3 空闲查询开销核对

计数场景：已有用户、v2 会话与 `AgentRuntimeState`；无新事件、无任务；依次调用一次 `authorize()` 和一次 `read_stream()`。数据库替身返回空列表或既存行，记录真实函数发起的查询操作，不访问生产数据库。

| 查询 | 次数 |
| --- | ---: |
| 用户状态、会话可见性 | 2 |
| Worker 桥接：锁定会话行、读取运行状态 | 2 |
| Worker 桥接：读取增量 outbox、检查是否还有未消费 outbox、查询终态任务 | 3 |
| 读取 `SessionStream` 增量 | 1 |
| 合计 | **8** |

该路径还进入 **3 个数据库 Session 作用域**，包含 **1 次 `SELECT … FOR UPDATE`**。Session 作用域数不代表同时占用的物理连接数。重复执行 100 次出站帧权限检查，对应 200 次查询调用。

默认循环在每轮工作后睡眠 0.1 秒。若忽略查询耗时，名义频率约为 10 轮/秒，即单连接约 80 次查询/秒；N 条同类连接约为 80N 次/秒。这是路径推算，实际频率受 I/O 耗时影响，尚未计入心跳、出站帧、轨迹及历史任务额外查询。

复核方法：在隔离数据库/测试替身中固定上述条件，记录 `authorize → read_stream → bridge_worker → stream` 的调用；真实 PostgreSQL 复核时另计连接探活、事务控制、SQL 时长和锁等待，不把本次替身计数当作数据库压测。

## 3. 优化项与代码依据

以下优先级表示实施顺序，不是已经证明的生产事故等级。O1–O9 的依据描述检查基线；O3/O5/O7 的本次实现和验证结果见 §6.1，其余仍为后续方案。

### O1：空闲 WS 高频查询（高）

- 依据：[ws_v2.py](../backend/api/app/routers/ws_v2.py) 的 `WsV2Connection.__init__ / stream`，默认 `poll_interval=0.1`；[loop_service.py](../backend/api/app/agent/loop_service.py) 的 `read_stream` 每次先桥接 Worker，再读流。
- 影响：没有新消息时仍反复访问数据库；同会话多个观察者各自运行这一循环。
- 首选改法：优先同会话共享增量读取，减少多个观察者的重复工作；已提交事件触发唤醒，活动链路快速读取；满页积压不固定等待每页 100ms。只有通知覆盖及兜底时效通过验收的空闲路径才启用有上限的退避。发送/取消/交互命令不依赖读取定时器。
- 边界：通知仅是唤醒提示，PG 中已提交的连续游标才是事实；同会话共享读取只在各观察者游标所需范围相同或被有界缓存覆盖时复用，落后的观察者独立补读。出站帧仍按接收者实时授权和脱敏。进程内通知不能覆盖其他 API 副本及 Worker；这些路径没有可靠唤醒前保持满足时效预算的兜底频率，不能全部降为低频读取。等待注册与高水位复查须避免丢失唤醒，通知合并不能丢持久事件。批量追赶仍须让出事件循环并受发送队列约束。
- 验收：空闲查询显著下降；取消、权限撤销、Worker 更新、跨实例写入和断线补发时效不超出预先冻结的预算。

### O2：Worker 桥接与终态补偿反复扫描（高）

- 依据：[agent_events.py](../backend/api/app/harness/memory/agent_events.py) 的 `bridge_worker / _transaction / _has_task_frame`。
- 影响：每次桥接都锁会话行；追平 outbox 后仍查询该会话全部终态任务，逐个判断报告和结束投影是否已存在。多个观察者还会竞争同一会话行锁。
- 首选改法：将 outbox 增量消费与终态补偿分开调度；新进度和终态优先桥接，不等待低频历史补偿。空闲且无新候选时避免无意义的写锁事务；终态补偿采用有界批次，批量检查投影存在性，并与 O1 配合同会话共享桥接工作，减少重复扫描和锁竞争。
- 边界：只读预检不能替代写入事务内复验；不能仅凭任务时间戳简单跳过迟到报告。继续保留 Worker 未发布、丢失、乱序到达时的补偿能力，以及进度先于终态的既有规则。
- 验收：终态事件和报告幂等；重复执行不增投影；在历史任务数增长时，单次空闲补偿工作量有界；多观察者下锁等待下降。

### O3：后台空闲连接累积（高）

- 依据：[store.ts](../frontend/src/agent/loop/store.ts) 的 `clients / open / remove / close`；会话切换只打开目标连接，未针对空闲旧连接做淘汰。
- 影响：同一页面依次访问多个会话，可能同时保留多条 WS、心跳和服务端读取循环；标签页不可见也不会自动暂停这些 WS。
- 首选改法：为连接增加独立于草稿/视图状态的空闲释放逻辑。当前会话、活动回合、待交互、请求结果未确认，以及仍需后台追踪 Worker 任务的会话保持连接；其他后台空闲会话经过宽限期后释放。快速来回切换期间不反复关闭连接；释放后以有界本地状态配合增量补发恢复，避免每次读取完整历史。
- 边界：不能以 `turn.end` 代表 Worker 已结束；不能调用现有 `remove()` 一并清空草稿。释放后再次 `open()` 必须能重连，不能返回已经关闭的实例。保存 cursor 必须同时保留与之对应的完整 reducer 状态；状态被淘汰则从 0 或授权快照恢复。
- 验收：依次打开 20 个已结束、无活动任务的会话后，宽限期结束只剩当前会话连接；分别比较保留连接与已释放连接的切回到可见/可发送延迟，不能只验连接数。切回历史无丢失、重复或乱序；恢复缓存不能绕过权限重验展示已撤权正文；后台活动回合、取消和交互行为保持正确。

### O4：每个流式片段重复鉴权与发帧（高）

- 依据：[loop.py](../backend/api/app/agent/loop.py) 对正文和思考增量分别发布；[ws_v2.py](../backend/api/app/routers/ws_v2.py) 的 `sender` 在每帧发送前调用 `authorize`，后者查询用户及会话。
- 影响：供应商分片越细、观察者越多，数据库查询、JSON 编码与网络发送次数越多。
- 首选改法：优先在浏览器传输投影层合并同一 session/turn/attempt/channel 的相邻瞬态片段，设置时间和大小双上限；保持模型事实处理与工具调度不变。首片不进入批量等待，后续短窗口合并；稀疏片段不能等到凑满字数才发送。只有端到端显示延迟达标且帧数/查询实际下降时才启用该窗口。
- 边界：明确合并后的 `chunk_index` 去重规则并验证既有 reducer；最终持久消息到达时正确结算或丢弃剩余瞬态，禁止终态之后追加旧片段。第一批不引入长期 ACL 缓存，不合并持久事件，不放松发送前的权限校验。
- 验收：文本与思考分流不变、最终内容一致、取消及时；小分片模型的帧数和鉴权次数下降，首片及后续显示延迟在预算内。

### O5：`agent-ui` 重复刷新与配置重复解析（中，适合先行实施）

- 依据：[AgentWorkspace.vue](../frontend/src/components/agent/loop/AgentWorkspace.vue) 的 `refreshUi`、30 秒定时器、focus 监听和会话 watch；`epoch` 只拒绝旧响应落地，不取消旧请求。
- 后端依据：[sessions.py](../backend/api/app/routers/sessions.py) 的 `_loop_ui` 枚举协议档、逐档授权并重复解析默认档；[loop_wiring.py](../backend/api/app/agent/loop_wiring.py) 的 `authorized_profile`、[profiles.py](../backend/api/app/routers/profiles.py) 的 `_profile_connection` 多次调用环境读取；[profile_env.py](../backend/api/app/profile_env.py) 每次读取均读文件并解析。
- 首选改法：同一身份/会话请求合并，focus 刷新节流，切会话取消过期请求。后端先采用请求作用域内的一份配置文件快照，复用本次已解析的默认模型候选；首屏与新会话首次能力读取立即执行。延长周期刷新间隔只作为次要措施，须满足配置新鲜度与权限预算；已有有效状态不因后台刷新临时清空，不能让发送按钮为重复配置请求额外等待。
- 边界：请求去重优先于取消，因为 HTTP 中止不保证后端同步计算立即停止。静态配置与动态权限/控制状态分别处理，不能缓存整个响应后长期复用；注销或账号切换清理缓存。每次实际回合、工具执行和发送仍实时校验权限与配置。
- 验收：同作用域最多一个刷新请求在途；聚焦与定时器重叠不重复请求；旧会话响应不会覆盖新会话；配置修改可在约定时限内生效。若后续采用跨请求缓存，必须单独设计文件修改与配置保存的失效机制。

### O6：重连预先生成完整历史快照（中）

- 依据：[ws_v2.py](../backend/api/app/routers/ws_v2.py) 的 `stream` 在判断 cursor 前调用完整 `snapshot`；[agent_events.py](../backend/api/app/harness/memory/agent_events.py) 的 `snapshot` 在会话行锁下遍历历史帧，组装 timeline、消息及多个读模型。
- 影响：即使客户端已有有效游标，只需补发少量事件，也先承担全量历史读取、复制和归并；长会话重连可能延长锁持有时间。
- 首选改法：拆分轻量订阅元信息与完整快照的构造，正常增量续传只取授权后的高水位、保留边界和控制信息；确需 `resync.required` 时才构建完整快照。随后评估回合内全量 `log.read()` 的重复读取是否可复用同一一致性边界的事实前缀。
- 边界：不能在不同事务拼出不一致的 H 和快照；不能把裁剪后历史伪装成完整状态。跨回合缓存须保留 provider opaque state、工具回填与故障恢复事实。
- 验收：有效游标重连不再构造完整快照；过期/超水位/缺号仍正确 resync；并发追加、撤权和恢复场景不丢事件。

### O7：会话列表逐行查任务且无分页（中）

- 依据：[sessions.py](../backend/api/app/routers/sessions.py) 的 `list_sessions / _session_out`：列表 `.all()`，每个会话再查一次活动任务；工作区名称已批量预取。
- 首选改法：参照工作区名称预取，一次批量取得本次会话集合的活动任务，并保持每会话选取最新任务的语义。将分页作为独立契约迭代，避免与第一批减负混合。
- 验收：活动任务查询次数不随列表会话数线性增长；排序、共享可见性和任务摘要保持一致。大集合按数据库参数限制分批，不能把批量查询变成无限 IN 列表。

### O8：服务端闲置 Runtime 缺少淘汰（中）

- 依据：[loop_service.py](../backend/api/app/agent/loop_service.py) 的 `entries / _locks / detach / _finish / close`：回合结束会释放 writer 和本轮客户端资源，但普通 detach 不移除 Runtime，`entries.pop` 位于服务关闭流程。
- 影响：长期服务中，曾经运行过的会话 Runtime、图、锁及相关内存可能累积；这不等于空闲会话仍占用 writer 数据库连接。
- 首选改法：为无观察者、无活动回合、无交互/断线宽限任务且清理已完成的 Runtime 建立有界空闲回收；空闲期限与容量上限同时约束，热点会话允许短期复用但不能无限驻留。锁对象只能在确认无持有者和等待者时移除，不能产生同会话双锁。
- 边界：回收不删除持久日志、审批事实或执行隔离记录；恢复中的会话不得淘汰，未知执行不能因回收而被解锁。
- 验收：固定并发、持续创建并结束会话后，驻留对象数量与内存趋于稳定；分别测量热复用与淘汰后重建耗时。重开能恢复事实，不产生重复执行或控制权错配；不能通过过度淘汰造成持续重建、CPU 上升和首字变慢。

### O9：同步数据库操作占用异步事件循环（中，先测量再扩大范围）

- 依据：[loop_service.py](../backend/api/app/agent/loop_service.py) 的异步 `authorize / read_stream` 内直接执行同步 ORM/日志读取；[db.py](../backend/api/app/db.py) 使用同步 SQLAlchemy engine/session。
- 影响：数据库延迟和锁等待可能阻塞 WS 所在事件循环，影响同进程其他连接的接收、发送和取消。
- 首选改法：先通过 O1–O7 削减工作量；仍有可测阻塞时，对独立只读热点采用受限线程卸载或异步数据库访问。不得将全栈 AsyncSession 迁移作为第一批前置。
- 边界：每个并发单元独立创建/关闭 Session，只返回安全 DTO；禁止跨 Session 传 ORM 对象，禁止直接把持有 writer 物理连接的事务搬到其他线程。并发上限需要与连接池容量匹配。
- 验收：注入数据库延迟时事件循环延迟和取消响应改善；连接池没有因并发卸载而耗尽，持锁写者身份与事务原子性保持不变。

## 5. 验收方法与指标

### 5.1 场景矩阵

| 场景 | 建议固定负载 | 核对内容 |
| --- | --- | --- |
| 空闲页面 | 1 / 10 / 50 个隔离环境连接，分别持续 10 分钟 | SQL/秒、锁事务/秒、HTTP 请求数、CPU、连接池占用 |

| 流式回复 | 确定性模型替身输出相同内容，分别切成 100 / 1000 个 chunk | 下行帧数、鉴权次数、首片及末片耗时、最终文本一致性 |
| 唤醒及降级 | 本进程/API 其他副本/Worker 分别提交；注入通知丢失、合并、重复和恢复 | 正常及兜底事件可见延迟、查询次数、通知等待不丢唤醒；取消不受退避影响 |
| 热冷切换 | 宽限期内往返、连接释放后切回、Runtime 淘汰后发送 | 视图可见、连接就绪、可发送与首字的独立延迟；重建 CPU、内存及缓存命中 |

| Worker 历史 | 0 / 100 / 1000 条终态任务，包含重复、缺失及迟到报告 | 空闲补偿成本、任务/报告去重、顺序及最终一致性 |
| 撤权与故障 | 共享收回、账号禁用、断网重连、服务重启、跨实例写入 | 不泄露撤权后的帧，不重复工具副作用，不误解锁未知执行 |
| 长时间运行 | 固定活动并发，持续创建/完成会话 | Runtime/锁/订阅者数量、RSS 趋势和数据库连接归还 |

压力场景优先在隔离环境执行。生产验证仅使用 `qa-test`，先低负载验证并记录观察窗口；禁止使用 admin 创建跑测会话或污染业务任务。模型性能使用确定性替身隔离供应商波动，真实模型另做少量冒烟验证。

### 5.2 记录口径

- 数据库：应用业务查询、事务、行锁等待、查询耗时、连接池等待分别统计；已有 `pg_stat_statements` 可用时按指纹聚合，否则采用脱敏应用侧计数，不为本次检查擅自改生产数据库配置。
- API/WS：CPU、RSS、事件循环延迟、连接数、入站/出站帧数、队列溢出与重连次数；指标标签不使用 session_id、request_id 等高基数字段。
- 延迟：分别记录提交到受理、平台准备、模型首 token、服务收到片段到浏览器显示、取消到终态、事件提交到可见、重连到 replay.completed。已有统计不足时先补隔离观测，不能以模型耗时替代平台耗时。
- 每组记录代码 SHA、操作系统/Python/数据库版本、API 副本数、池配置、历史规模、并发连接、协议档数量和模型替身分片策略；至少重复 3 轮，报告样本量、P50/P95、样本足够时的 P99 和异常值。冷热场景单列，前后交错执行以降低环境漂移影响；样本不足则不能声称高分位延迟达标。
- 资源收益同时按单位时间和单位成功完成回合记录：CPU 时间/回合、SQL/回合、传输字节/回合，以及空闲 SQL/秒。比较同等输入到达率下的完成吞吐、错误率和队列积压，防止因处理变慢而出现“每秒资源减少”的假收益。
- 原始载荷不记录 API Key、Cookie、短票、密码、完整提示词或工具敏感正文。计数、类型、时间和大小足以支撑第一批判断。

### 5.3 速度与资源双门禁

S0 必须在实施前填写并冻结每个场景的绝对延迟上限、基线测量波动范围、资源上限和最低收益；不能在优化后扩大容差来迁就变慢。真实供应商首 token 不可由平台保证，平台新增等待和确定性替身端到端延迟必须可测、可控。

| 维度 | 速度门禁 | 资源门禁 |
| --- | --- | --- |
| 首屏/发送/首字 | 不增加等待周期或额外串行前置请求；P50/P95 不出现超出冻结测量误差的退化，并满足绝对预算 | 重复 HTTP、配置文件解析及前置 SQL 减少，错误率不升高 |
| 流式与终态 | 首片直发，后续有时间/大小上限；不为凑批拖延审批卡、取消或持久终态 | 帧数、鉴权查询、CPU 时间/回合和字节数有可验证下降；队列内存有界 |
| 事件唤醒 | 同进程、跨进程、Worker 与通知失效时分别达标；兜底上限按故障时效预算选取 | 空闲查询下降；通知或共享缓存不能引入无界队列和高频自唤醒 |
| 会话切换/重连 | 热切换、连接释放后切回、Runtime 重建分别达标，不能只展示最快场景 | 后台连接、Runtime 和恢复缓存均有容量约束，频繁重建成本不抵消节省 |
| 固定输入负载 | 完成吞吐不降低，错误率、队列等待不恶化；覆盖正常与设计峰值并发 | API、PG、浏览器分别核算 CPU/内存/网络，不能把压力转移到另一端后仍宣称整体减负 |

对于需要用少量有界内存换取大量重复查询的方案，先登记容量上限与预期取舍，再在表内各端资源预算中验收；不要求每项指标都机械下降，但不得超出任何已冻结预算。

### 5.4 候选收益目标

以下是待 S0 确认的验收目标，不是已实现收益或当前生产 SLA：

1. 完成 S1–S2 后，在同等空闲连接/历史规模下，使业务查询次数相较基线下降至少 80%，且 §5.3 速度门禁同时通过；单独 S1 如未达到该目标，明确登记残余热点，不靠延长等待凑数。
2. 同一作用域 `agent-ui` 同时在途请求不超过 1 个；定时器与 focus 重叠不重复刷新。
3. 20 个无活动回合、无交互、无 Worker 任务的历史会话切换后，空闲释放期结束仅保留当前会话连接。
4. 正常有效游标重连不构造完整历史快照；活动任务查询改造后不再每会话单查。
5. 首片、取消、Worker 更新、撤权、冷热切换和重连时效预算先测后冻结；资源收益不能以超出该预算为代价。任何事件丢失、重复副作用、权限泄露或错误解锁均直接判为验收失败。延迟变差但资源下降，或速度提升但资源预算超限，都不属于本方案验收通过。

### 6.2 审查问题修复（V0.4）

P2：旧实现只在每 15 秒的清理扫描中检查活动状态。如果后台共享会话第 50 秒开始回合、第 58 秒结束，两次扫描之间发生的活动不会重置旧计时，第 60 秒便会关闭实际只空闲 2 秒的连接；短 Worker 任务也存在相同问题。

修复位置为 `store.ts` 的 `onFrame`：对 transport 已去重的持久业务事件和有效 `assistant.*` 瞬态增量，在后台会话中立即记录本地接收时间。清理仍执行原有活动/权限/未知执行保护，心跳、订阅控制帧与诊断帧不延长宽限期；没有新增定时器、网络请求或数据库访问。

新增 3 项回归先在旧实现上失败，再在修复后通过：短回合、短 Worker 任务结束后完整等待 60 秒（包含 59999ms/60000ms 边界）；有效模型增量重置时间，同时持续 `pong` 不阻止回收。前端完整单测 **83 passed**，连接恢复、首次订阅超时与后台多步工具交互页面回归 **3 passed**，typecheck/build 通过。本次未修改后端，§6.1 的后端及完整页面测试结果为前一版本的验证记录；生产联合性能门禁仍待执行。
